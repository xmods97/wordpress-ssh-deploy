# План разработки

Этот документ является живым планом развития `wordpress-ssh-deploy`.
Он описывает порядок разработки проекта, а не последовательность действий
пользователя во время deploy.

## Статусы

- `не начато` — работы по пункту не начинались;
- `в работе` — пункт реализуется, но ещё не прошёл все проверки;
- `выполнено` — реализация и относящиеся к ней проверки завершены;
- `заблокировано` — продолжение требует решения или внешнего условия;
- `отложено` — пункт сознательно исключён из текущей версии.

Пункт получает статус `выполнено` только после проверки изменений и просмотра
итогового diff. Частично завершённые подпункты отмечаются отдельно.

## Правила ведения плана

1. После каждого этапа обновлять статусы этапа и его подпунктов.
2. Новые риски фиксировать в `docs/RISKS-RU.md`.
3. Если новый риск требует разработки, добавлять соответствующий пункт в этот
   план сразу после этапа, от которого зависит исправление, а не в конец файла.
4. Для нового пункта указывать связанный риск в формате `R-NNN`.
5. Не менять порядок уже выполненных этапов без отдельного объяснения.
6. Реальный deploy, импорт production-БД, push, release и публикация требуют
   отдельного явного разрешения и не считаются обычной проверкой разработки.

## Этап 6. Обратная синхронизация

**Статус: в работе**

Направление pull построено на принципе side-by-side: pull никогда не пишет в
рабочую локальную БД и рабочие файлы. Из-за этого локальный rollback не нужен и
намеренно не реализуется — при ошибке рабочая копия просто не менялась.

- [x] Реализовать получение БД с сервера (режимы `pull-db`, `pull-full`,
  экспорт через protected runner, скачивание в отдельный workspace).
- [x] Проверять SQL до любого использования: gzip integrity, структура дампа,
  точное число таблиц, prefix, отсутствие чужих и смешанных идентификаторов.
- [x] Получать uploads через временный каталог (`pull-files`, additive,
  распаковка только в staging directory после проверки листинга).
- [x] Не удалять рабочие uploads до проверки новой копии — рабочие файлы не
  заменяются вообще; mirror-режим определён контрактом, но fail-closed.
- [x] Запретить pull для production на трёх независимых уровнях.
- [x] Покрыть контракт, политику путей, верификаторы и CLI-обвязку mock-тестами.
- [ ] Создавать проверенный локальный backup перед импортом — требуется только
  на будущем шаге активации; сейчас импорт в локальную БД не выполняется.
- [ ] Выполнять serialized-safe замену URL через WP-CLI после активации.
- [ ] Реализовать активацию скачанной копии отдельной явной командой.
- [ ] Обновить runner на staging и провести первый реальный pull.
- [ ] Решить, нужен ли отдельный ожидаемый счётчик таблиц для направления pull.

**Связанные риски:** R-032, R-033, R-034, R-035, R-036.

**Проверено только локально:** реальный pull не выполнялся ни разу; режимы
runner проверены статическим анализом и `sh -n`, но не исполнением.
