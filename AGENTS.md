# Глобальные правила проекта для Codex

## Обязательное чтение перед работой

Перед началом задачи прочитай:

1. этот файл;
2. `.ai/STATE.md` и выбранный блок текущего `TASK_ID`;
3. `.ai/HANDOFF.md`, только если `HANDOFF_STATUS: READY`;
4. `.ai/POLICY.md`, если задача критическая, есть конфликт ролей или требуется передача управления;
5. только последние релевантные записи `.ai/CHANGELOG.md`.

Не перечитывай весь журнал без необходимости.

## Определение роли

Высший приоритет всегда имеет пользователь.

Перед изменениями определи конкретный `TASK_ID` из `ACTIVE_TASK_IDS`. Не работай одновременно в нескольких задачах одной сессии.

Порядок назначения:

1. `TASK_LEAD` выбранной задачи;
2. владелец `DOMAIN`;
3. `PROJECT_LEAD`;
4. ревьюер или резервный агент.

Не меняй роль, владельца направления, блокировку, ветку или главного агента без явного разрешения пользователя.

Окончание лимита, отсутствие ответа или недоступность другого агента не являются разрешением принять управление.

## Строка перед содержательной задачей

Кратко сообщи:

**Роль: [главный агент / ревьюер / резервный]. Рекомендация: [доступная модель], [уровень усилия] — [причина]. Маршрут: [Codex / Claude Code / обычный чат]. Контекст: [нормальный / перегружен]. Лимит: [нормально / экономить / остановиться после этапа].**

Используй только реально доступные модели и режимы. Не выдумывай точный остаток токенов.

Предлагай минимальную модель и минимальное усилие, достаточные для надёжного результата.

Более сильную модель рекомендуй для архитектуры, сложной диагностики, безопасности, production, базы данных, платежей, инвойсов, деплоя, rollback, критических расчётов и взаимозависимых систем.

## Когда предложить обычный чат

Предлагай обычный чат только при полной уверенности, что задачу можно завершить без:

- доступа к репозиторию;
- чтения или изменения файлов;
- запуска команд;
- тестов и сборки;
- `git diff`;
- проверки интеграции;
- проверки фактического состояния проекта.

Подходящие задачи:

- тексты;
- идеи;
- названия;
- объяснение концепции;
- требования;
- предварительное обсуждение без анализа репозитория.

Если есть значимый риск неполного результата, не предлагай перенос.

## Контекст и лимит

Если история перегружена и возникает риск потери деталей, повторного исследования или лишнего расхода, сообщи:

**Контекст задачи перегружен — лучше продолжить в новой задаче.**

Подготовь handoff до 250 слов:

- цель;
- выполненное;
- изменённые файлы;
- проверки;
- нерешённые вопросы;
- риски;
- следующий шаг.

Новую задачу создавай только после подтверждения пользователя.

В естественной точке остановки сообщи:

**Лимит: лучше остановиться после текущего этапа — следующая часть может потребовать значительного расхода.**

Не повторяй предупреждение после каждой мелкой операции.

## Git и совместная работа

- Используй ветку вида `agent/task-slug`.
- Не изменяй ветку и worktree другого агента.
- Не работай одновременно над одними файлами в одной рабочей копии.
- Перед изменениями проверь текущую ветку, `git status`, базовый commit и `WORK_LOCK`.
- Для review сначала проверяй `git diff`, изменённые файлы, прямые зависимости и результаты уже выполненных проверок.
- Не перезаписывай чужие незакоммиченные изменения.

- При нескольких активных задачах проверяй, что текущая ветка, worktree, `WORK_LOCK` и `ALLOWED_FILES` принадлежат выбранному `TASK_ID`.
- Если другая активная задача затрагивает те же файлы или зависит от незакоммиченных изменений, переведи текущую задачу в `BLOCKED` и сообщи пользователю.
- Не выполняй merge, force push, rebase опубликованной ветки или production-деплой без правил из `.ai/POLICY.md`.

## Выполнение

Для простых задач действуй сразу.

Не составляй отдельный план, если задача содержит менее трёх существенно зависимых шагов.

Сначала проверяй наиболее вероятные файлы и причины.

Не запускай субагентов, параллельные исследования или полный аудит без явного запроса пользователя.

После изменений запускай только минимальную релевантную проверку.

Не показывай длинные логи, полные файлы и промежуточные рассуждения.

В финале сообщай только:

- результат;
- изменённые файлы;
- проверки;
- важные риски;
- следующий шаг, только если работа не завершена.

Если задача выполнена, остановись.

## Обновление состояния

После законченного этапа:

1. обнови `.ai/STATE.md`;
2. добавь краткую запись в `.ai/CHANGELOG.md`;
3. обнови `.ai/HANDOFF.md` только при передаче, перегруженном контексте или смене сессии.

Не переписывай старые записи журнала.


## Правило Codex

Если главным назначен Claude, Codex работает только как ревьюер или консультант, пока пользователь явно не передаст управление.

Codex не снимает `WORK_LOCK: CLAUDE` и не изменяет ветку Claude.


## Критический риск, найденный при review

Если при review обнаружен критический риск вне текущей области задачи, обязательно сообщи пользователю. Для сообщения разрешение не требуется.

Не исправляй проблему и не расширяй область задачи без отдельного разрешения.


## Режим существующего проекта

Этот шаблон установлен в уже существующий проект, который ранее вёл Codex.

При первом запуске:

1. Сохрани роль `PROJECT_LEAD: CODEX`.
2. Сохрани роль `TASK_LEAD: CODEX` для всех уже начатых задач.
3. Сохрани `WORK_LOCK: CODEX`.
4. Назначь Claude только как `REVIEWER: CLAUDE`.
5. Синхронизируй `.ai/STATE.md` с фактической веткой, commit, git status, изменёнными файлами, проверками и следующим шагом.
6. Не меняй рабочий код во время первичной синхронизации.

Claude не получает управление из-за окончания лимита Codex. Для отдельной задачи или передачи управления требуется явная команда пользователя.

После выполнения Claude отдельной задачи Codex остаётся главным проекта, проводит review и решает вопрос интеграции.

## Рекомендация подходящего исполнителя

Перед содержательной задачей оцени, какой инструмент лучше подходит для её полного, качественного и безопасного выполнения:

- Codex;
- Claude Code;
- обычный Claude Chat;
- обычный ChatGPT;
- текущий агент без переключения.

Учитывай:

- необходимость доступа к репозиторию и фактическим файлам;
- объём и сложность кода;
- продолжение уже накопленного проектного контекста;
- архитектуру, UX, дизайн и работу с требованиями;
- безопасность, production, базу данных, деплой, платежи, инвойсы и расчёт стоимости;
- необходимость запуска команд, тестов, сборки и анализа `git diff`;
- необходимость независимого review;
- текущий размер контекста и расход лимита.

Если другой инструмент заметно лучше подходит, кратко сообщи:

**Рекомендация по исполнителю: [инструмент] — [одна конкретная причина].**

Также укажи рекомендуемый режим:

- передать задачу полностью;
- запросить консультацию;
- запросить независимый review;
- поручить отдельный независимый этап;
- продолжить текущим агентом и привлечь второго после checkpoint.

Рекомендация носит только консультативный характер.

Она не:

- меняет `PROJECT_LEAD`;
- меняет `TASK_LEAD`;
- передаёт `WORK_LOCK`;
- разрешает изменение кода;
- создаёт ветку или worktree;
- запускает передачу автоматически;
- заменяет явное решение пользователя.

Окончательное решение всегда принимает пользователь.

Если текущий агент способен выполнить задачу надёжно и без заметного снижения качества, не предлагай переключение только из-за небольшого преимущества другого инструмента.


### Когда Codex особенно уместен

Codex обычно предпочтителен для:

- основной реализации в существующем репозитории;
- продолжения уже начатой Codex задачи;
- точечных PHP, JavaScript, WordPress и WooCommerce изменений;
- Git, `diff`, тестов, сборки и команд;
- сложной отладки интеграции;
- скриптов деплоя и автоматизации;
- задач, где Codex уже накопил качественный контекст.

### Когда стоит рассмотреть Claude

Claude Code или Claude Chat можно рекомендовать для:

- UX и дизайна;
- анализа пользовательских сценариев;
- архитектурной критики;
- независимого review безопасности;
- проверки бизнес- и финансовой логики;
- структурирования требований;
- работы с большими текстовыми материалами.

Это не жёсткое разделение. Решение зависит от конкретной задачи.
